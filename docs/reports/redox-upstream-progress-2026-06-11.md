## Recent Community Signals

The latest public Redox news entry found in this refresh remains the
2026-05-31 monthly report; no June 2026 monthly report was visible on the
official news index as of 2026-06-11 03:17 Asia/Shanghai. A separate
2026-03-17 capability-security article remains directly relevant to Cocoon.

The May report shows active funded development: Redox Summer of Code 2026 funds
two student projects, one on scheduling and one on relibc/POSIX compatibility,
and Redox is also funding three non-student contributors. That matters because
Redox is not merely accepting sporadic patches; it is organising paid work
around kernel performance, compatibility, and the service substrate.

The technical progress is aligned with Cocoon's risk surface. EEVDF/DWRR
scheduling, faster `poll`/`epoll`, RedoxFS inode caching, futex work, and
runtime race fixes reduce the operational risk of long-running services.
Cookbook recipe rules, rollback, package-web browsing, and faster package
updates improve the native distribution path. Relibc work on POSIX conformance,
`openat2`, `utimensat`, headers, tests, and `*at` migration is especially
important for a launcher that treats already-open FDs and CWD as authority.

The March capability-security post is the strongest design signal for Cocoon.
It describes open file descriptors as capabilities, a userspace namespace
manager, namespace-as-FD handling, and CWD-as-FD handling. That maps closely to
Cocoon's current review package around restricted namespaces, preopened
resources, FD-only execution, permission diffs, and receipt evidence.

The 2025/26 priorities post gives the grant narrative a public anchor: Redox is
explicitly interested in hosted Redox for web services, Redox Server for edge
and cloud, lightweight sandboxing, secure service hosting, repeatable builds,
management tooling, compatibility, performance, and security.

## Judgement

**Relevant: yes, high.** Redox community progress is now directly relevant to
Cocoon, not just philosophically adjacent. The moving parts are the same:
namespace visibility, file-descriptor authority, CWD as capability, relibc
`openat` semantics, package identity, Redoxer/QEMU evidence, and native
Cookbook packaging.

**Valuable: yes, high, if Cocoon stays narrow.** Cocoon is valuable as an
authority, policy, permission-diff, receipt, and audit layer above native Redox
mechanisms. It is not valuable as a parallel package manager, a generic Docker
analogue, or a self-invented sandbox competing with Redox namespaces and
schemes.

**Grantable: yes, medium-high.** The case is credible because Redox already has
NLnet/NGI-funded operating-system work in capability security, ring-buffer I/O,
and Unix-style signals, and the Redox priorities page explicitly welcomes
Redox-adjacent grant work. Cocoon is grantable if framed as upstream-aligned
integration and evidence work for secure hosted/server Redox services. It is
not yet grantable as a claim of production-ready arbitrary service isolation.

## Strong Grant Scope

1. Upstream-reviewed Cocoon authority boundary for FD-only service launch under
   Redox namespaces.
2. A Redoxer/QEMU evidence lane proving allowed preopens, denied ambient access,
   structured child results, and receipt auditability.
3. A Cookbook recipe and package-staging path that leaves payload ownership with
   `pkg`/`pkgar`.
4. A compatibility test pack for relibc `openat`, CWD-as-capability, namespace
   visibility, denied schemes, and long-running service behaviour.
5. Permission-diff and signed-receipt tooling for hosted Redox services.

## Weak Grant Scope

1. A competing Redox package manager.
2. A broad container platform without an accepted Redox launcher boundary.
3. A production-ready claim for arbitrary services before Redox/QEMU evidence
   and upstream review are both complete.
4. Desktop-first work unless it is explicitly tied to sandboxed application
   authority and user-visible permission review.

## Decision

Proceed with Redox-aligned grant preparation and upstream review. Keep Cocoon's
production label blocked.

Cocoon may currently claim:

```text
authority_mode = redox-enforced-capsule-entrypoint
authority_enforced_for_review_fixture = true
production_arbitrary_service = false
```

Cocoon should not claim:

```text
authority_mode = redox-enforced
production_arbitrary_service = true
```

The next useful action is to prepare a concise upstream review request around
whether FD-only execution from preopened executable resources is the intended
contract for secure service launch on Redox. The grant narrative should present
Cocoon as making Redox service authority reviewable and auditable, while Redox
keeps ownership of namespaces, schemes, relibc, package mechanisms, and final
enforcement semantics.
