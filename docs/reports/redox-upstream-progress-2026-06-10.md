## Community Progress Signals

The latest official news item available on 2026-06-10 is the 2026-05-31 monthly
report. The relevant signals are:

1. Redox is funding active work through Redox Summer of Code 2026, including a
   new scheduler and relibc/POSIX compatibility work. The report also says
   Redox is funding three other non-student contributors and is spending beyond
   current monthly donations.
2. Kernel and runtime performance are improving: EEVDF/DWRR scheduler work,
   faster `poll`/`epoll`, futex improvements, I/O event timeout work, RedoxFS
   inode caching, and possible EBADF race fixes.
3. The package and build story is improving: package updates now complete in
   minutes rather than hours, package web browsing exists, and Cookbook recipe
   rules plus rollback make recipe debugging more practical.
4. Compatibility work is substantial: relibc gained more POSIX functions,
   headers, `*at`-style migration, tests, and documentation; the Rust compiler
   fork was updated to 1.98 nightly.
5. Capability/security-adjacent work is visible: the May report includes
   `relpathat` for `ramfs`, file-table flexibility, and multiple-`fds` variants
   for `call` and `std_fs_call`.
6. Desktop progress is real but secondary for Cocoon: XFCE, COSMIC Monitor,
   graphics, terminal, and UI improvements show ecosystem maturity, not a direct
   service-authority dependency.

The 2025/26 priorities post is highly aligned with Cocoon. Redox explicitly
calls out hosted Redox as a VM-based web-services runtime, Redox Server for
edge/cloud, lightweight sandboxing, repeatable builds, compatibility,
performance, security, and management tooling.

## Judgement

**Relevant: yes, high.** The recent Redox work touches Cocoon's exact risk
surface: relibc open/fd semantics, runtime process behaviour, build recipes,
Redoxer/QEMU evidence, package identity, and Redox's stated goal of secure
service hosting.

**Valuable: yes, high, if Cocoon stays thin.** Cocoon should remain an
authority, policy, diff, receipt, and audit layer above Redox mechanisms. The
valuable contribution is not a competing package manager, service supervisor,
or generic sandbox. It is a reviewable layer that proves service authority using
Redox namespaces, schemes, already-open FDs, and native package artefacts.

**Grantable: yes, medium-high.** The grant case is credible because Redox is
actively seeking and using grant-style funding, including NGI Zero/NLnet work,
and because Cocoon maps onto Redox's public hosted/server/security priorities.
It becomes weak if framed as "production Redox service platform" today. It is
strong if framed as upstream-aligned evidence and integration work.

## Grantable Scope

Good grant scope:

1. Upstream-ready Cocoon Cookbook recipe and packaging evidence.
2. `pkgar`-backed payload prototype that preserves Cocoon manifests,
   permission diffs, receipt hashes, rollback metadata, and audit readback.
3. Redoxer/QEMU CI hardening for Cocoon authority smoke tests on capable
   runners.
4. Maintainer review of the FD-only service launcher boundary before promoting
   `redox-enforced-capsule-entrypoint` to final `redox-enforced`.
5. A narrow compatibility test pack covering relibc `openat`/fd semantics,
   runtime schemes, CWD-as-capability, and denied ambient access.

Poor grant scope:

1. A parallel Redox package manager.
2. A generic container platform without an accepted Redox launcher boundary.
3. A claim that Cocoon is already production-ready for arbitrary services.
4. Desktop-first work, unless it is specifically about sandboxed application
   authority and user-visible permission review.

## Current Decision

Proceed with Redox-aligned grant preparation, but keep the production label
blocked.

Cocoon may claim:

```text
authority_mode = redox-enforced-capsule-entrypoint
authority_enforced_for_service = true
production_arbitrary_service = false
```

Cocoon should not yet claim:

```text
authority_mode = redox-enforced
production_arbitrary_service = true
```

The next useful action is to prepare a short upstream review ask around
launcher correctness, runtime scheme minimums, and packaging ownership. The
grant narrative should state that Cocoon complements Redox by making service
authority auditable while leaving enforcement, namespaces, schemes, libc, and
package mechanisms with Redox.
